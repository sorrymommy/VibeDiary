# QA 기록: 음성이 일부만 글로 옮겨지는 문제

- 날짜: 2026-10-28
- 계기: 사용자 제보 "음성이 텍스트로 변환되는데 전부 변환되지 않는 것 같다"
- 방식: 실제 폰에서 진단 로그로 원인 확인 → 실험으로 수정 방향 결정 → 수정 → 별도 서브에이전트의 시니어 QA(3차까지) → 지적 사항 수정
- 대상 파일 (`AOS/app/src/main/java/com/vibediary/app/` 기준)
  - `ai/Transcriber.kt` (주 수정 대상)
  - `ai/AnalysisWorker.kt`
  - `ui/newentry/NewEntryViewModel.kt`, `ui/newentry/NewEntryScreen.kt`
  - `capture/AudioRecorder.kt` (`BYTES_PER_SECOND` 공개)

> 줄 번호는 이후 수정으로 달라졌으므로 함수와 상황 기준으로 적었습니다.

## 원인 분석

### 진단 방법
- `Transcriber`에 임시 진단 로그(태그 `VD-STT`)를 넣었습니다. 기록한 항목: 시작, 입력 완료 시점, 부분 결과, 구간 결과, 오류, 세션 종료.
- 갤럭시 S23(Android 16)에서 정해진 5문장(약 45초)을 읽고 녹음했습니다.

### 로그로 확인된 사실 (45.6초 녹음)
| 시점 | 이벤트 |
|---|---|
| +313ms | 앱이 녹음 파일 전체(1.46MB)를 엔진 입력에 다 써 넣고 입력을 닫음 |
| +887ms | 구간 1개 인식: "오늘은 아침 일찍 일어나서 공원을" |
| +889ms | 엔진이 세션 종료 → 나머지 약 40초 분량이 처리되지 않고 버려짐 |

**원인:** 안드로이드 기기 내 음성인식 엔진은 입력을 **실시간으로 들어오는 소리**로 다룹니다. 앱이 파일을 한꺼번에 넣고 바로 입력을 닫자, 엔진은 첫 구간만 마무리하고 세션을 끝냈습니다.

### 넣는 속도 실험 (같은 녹음 파일, 임시 진입점으로 반복 실행)
| 넣는 속도 | 결과 | 걸린 시간 |
|---|---|---|
| 한꺼번에 (기존) | 첫 구간만: "오늘은 아침 일찍 일어나서 공원을" | 0.9초 |
| 4배속 | 구간 경계마다 단어 누락("산책했다 날씨가", "오후에는 카페에 앉아서", "하루를 마무리했다"), 끝부분 잘림 | 12초 |
| **2배속** | **5문장 모두 옮겨짐** ("새 앱"을 "새 에"로 오인식한 한 곳 제외) | **24초** |
| 1배속 | 2배속과 결과 동일 | 48초 |

→ **2배속 채택.** 오인식 한 곳은 엔진의 인식 정확도 문제로, 이번 수정 범위 밖입니다.

## 수정 내용
- `feedPaced()`: 녹음을 0.1초 단위로 끊어 **2배속**(`FEED_SPEED = 2`)으로 엔진에 넣고, 마지막에 1.5초 무음(`TAIL_SILENCE_MS`)을 붙여 끝 구간까지 마무리되게 함
- 구간마다 앞에 붙던 공백을 정리해, 문장 사이 공백이 두 칸이 되던 문제 수정 (`addBest()`)
- 진단 로그와 임시 진입점(`SttDiagReceiver`, 매니페스트 항목)은 모두 삭제하고 남은 흔적이 없는지 검색으로 확인

| # | 등급 | 문제 | 발생 상황 | 수정 내용 |
|---|---|---|---|---|
| 1 | Major | 긴 녹음은 백그라운드 분석이 영원히 끝나지 않음. 2배속이면 변환에 녹음 길이의 절반이 걸리는데, WorkManager는 작업을 약 10분 만에 멈춤. | 20분 녹음: 변환에 10분 이상 걸려 작업이 강제 중단되고, 재시도도 처음부터 다시 해서 같은 방식으로 중단됨. 기록이 분석되지도, 실패로 표시되지도 않음. | `transcribe()`에 시간 예산(`budgetMs`) 추가. 예상 시간이 예산을 넘으면 시작하지 않고 `Problem.TOO_LONG`으로 실패 처리. 백그라운드는 8분 예산, 새 기록 화면 미리보기는 예산 없음. |
| 2 | Minor | 세션이 일찍 끝나거나 취소돼도 녹음을 넣는 스레드가 계속 돌거나 막혀 있을 수 있음 | 변환 중 저장, 화면 이탈 | `AtomicBoolean` 정지 신호를 두고, 세션 종료나 취소 때 세움. 넣는 루프가 매번 확인. 스레드 이름 `transcribe-feed` 지정. |
| 3 | Minor | 미리보기 대기 시간이 녹음 길이의 절반으로 늘었는데 안내가 없음 | 5분 녹음: 2분 30초 대기 | 문구 "글로 옮기는 중이에요. 녹음 길이의 절반쯤 걸려요"로 변경 |
| 4 | Nit | 공백 정리 주석 위치, 대기 시간 계산이 넣는 속도와 연결되지 않음, 스레드 이름 없음 | — | 모두 정리 |

## 2차 QA

| # | 등급 | 문제 | 발생 상황 | 수정 내용 |
|---|---|---|---|---|
| 1 | Major | 대기 한도를 2배속 기준으로 줄였더니 너무 빡빡해짐 | 느린 폰에서는 엔진이 2배속을 못 따라가 입력이 실시간 속도로 느려짐. 6분 녹음이 매번 시간 초과로 실패. | 사전 판단(TOO_LONG)은 2배속 예상치로 하되, 실제 대기 한도는 **실시간 속도 기준**(녹음 길이 + 무음 + 여유)으로 하고 호출 측 예산을 넘지 않게 함 |
| 2 | Minor | 미리보기가 시간 초과를 포함한 모든 일시적 실패를 재시도함 | 시간 초과는 다시 해도 똑같이 실패하고, 대기만 두 배로 늘어남 | `Problem.BUSY`(엔진이 다른 작업 중, 오류 코드 8)를 따로 두고 이 경우만 재시도 |
| 3 | Minor | 정지 처리에서 다른 스레드가 쓰는 중인 입력(writeSide)을 밖에서 닫음. 파일 디스크립터 번호 재사용 위험. | 변환 중 취소 | 입력은 넣는 스레드만 닫도록 변경. 정지는 신호와 읽는 쪽 닫기로만 처리. |
| 4 | Minor | TOO_LONG 안내 문구가 이미 저장된 기록에는 어색함 ("녹음 직후 새 기록 화면에서는…") | 상세 화면 | "녹음이 너무 길어 백그라운드에서는 글로 옮기지 못했어요"로 변경 |
| 5 | Nit | `vm.transcriptProblem!!` 사용 | — | 지역 변수로 바꿔 `!!` 제거 |

확인된 정상 동작: TOO_LONG 경로는 기록을 실패로 표시하고 사유를 남기며, "다시 분석"을 눌러도 무한 반복하지 않음.

## 아직 확인하지 못한 것
- **최종 버전 실기기 재녹음:** 2배속 실험은 같은 알고리즘으로 확인했지만, QA 수정(정지 신호, 대기 한도, BUSY 재시도)이 들어간 최종 버전으로 새로 녹음해 끝까지 옮겨지는지는 아직 사용자 확인 전입니다.
- **긴 녹음:** 5분 이상, 그리고 TOO_LONG 기준(약 15분)에 걸리는 녹음을 실제로 녹음해 보지 않았습니다.
- **다른 기기:** S23보다 느린 폰에서 2배속을 따라가는지(대기 한도는 실시간 기준으로 잡아 둠)
- **엔진 바쁨:** 미리보기 변환 중 저장 시 백그라운드 재시도가 실제로 동작하는지 재현하지 못했습니다.
